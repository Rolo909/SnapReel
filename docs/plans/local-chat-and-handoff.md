## 1. Ключевые решения (нужно подтвердить)

### 1.1. Чем запускать языковые модели — **рекомендация: `llama-server` из llama.cpp как отдельный процесс**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **`llama-server` (готовые сборки llama.cpp)** ✅ | Готовые бинарники под Windows: CUDA, Vulkan (AMD и Intel), HIP, SYCL, CPU; GGUF-квантизации (модель 8B влезает в 6 ГБ); картинки и звук через `--mmproj`; OpenAI-совместимый API со стримингом и вызовом функций; падение модели не роняет программу; отмена = закрыть соединение | Нужно скачивать и проверять исполняемый файл; отдельный процесс делит видеопамять с torch |
| `llama-cpp-python` | Всё внутри Python | Под Windows с GPU колёса ненадёжны, часто нужна сборка компилятором — ломает установку «в один клик» |
| `transformers` (уже есть) | Без новых зависимостей | Без квантизации 8B-модель требует ~16 ГБ видеопамяти; медленно на CPU; сложно с vision-моделями |
| Ollama / LM Studio | Пользователь мог уже поставить | Внешняя программа, своя папка моделей, наш подбор под железо не работает |

Итог: основной движок — `llama-server`. **Дополнительно** (дёшево, т. к. API тот же): если на `localhost:11434` (Ollama) или `:1234` (LM Studio) уже что-то запущено — показать эти модели как «внешние» (`source: "online"`-подобный режим, без подбора под железо).

Сборка `llama-server` выбирается по видеокарте так же, как сейчас выбирается сборка PyTorch (`data/gpu_support.json`): `cuda` / `vulkan` / `hip` / `cpu` / `metal`. Версия закреплена в `data/llama_runtime.json` вместе с SHA-256 каждого архива; скачивается при первом открытии чата (как модель, с прогрессом), распаковывается в `<models>/runtime/llama/<версия>/`. Хост `github.com/ggml-org/llama.cpp/releases` разрешается **только** для этих закреплённых файлов, удалённый каталог не может подменить ссылку.

### 1.2. Распознавание голоса — **рекомендация: Whisper через `transformers`**

Новых зависимостей нет (torch и transformers уже стоят). Модели: `whisper-small` (лёгкая, CPU), `whisper-large-v3-turbo` (качество, GPU). Работает в своём маленьком потоке `SttWorker`, не трогая `GenerationWorker`. Альтернатива на потом — `faster-whisper` (быстрее на CPU, но +ctranslate2).

Запись с микрофона — `QtMultimedia` (`QMediaCaptureSession` + `QAudioInput` + `QMediaRecorder`), уже входит в PySide6.

### 1.3. Документы — опциональные зависимости

`pypdf` (PDF) и `python-docx` (Word) — в новый extra `docs`; без них вложение PDF/DOCX показывает понятную подсказку. Текст, Markdown, код, CSV, JSON читаются без зависимостей.

## 2. Языковые модели: каталог, подбор под железо, загрузка

### 2.1. Расширение `ModelSpec` (`core/catalog.py`)

```python
KINDS = ("image", "video", "speech", "chat", "transcribe")
ENGINES |= {"llama", "whisper"}

# новые поля ModelSpec (у прочих видов остаются пустыми)
quants: list[dict]        # [{"file": "...Q4_K_M.gguf", "gb": 4.9, "bits": 4.8}, ...]
mmproj: str = ""          # файл проектора для картинок/звука
context: int = 0          # максимальный контекст модели
layers: int = 0           # block_count
kv_gb_per_1k: float = 0.0 # KV-кэш на 1000 токенов при fp16
capabilities: list[str]   # vision | audio | tools | reasoning
```

`ModelStore` для GGUF хранит **один** выбранный файл квантизации + `mmproj`; в манифесте записывается, какая квантизация скачана.

### 2.2. Чтение GGUF (`core/llm/gguf.py`, новый)

Свой короткий парсер заголовка GGUF (магия, версия, пары ключ-значение; ~80 строк, без зависимостей): `general.architecture`, `*.block_count`, `*.context_length`, `*.attention.head_count(_kv)`, `*.embedding_length`, `tokenizer.chat_template`.

- Локальный файл — читаем заголовок напрямую.
- Файл на Hugging Face — HTTP-запрос с `Range` на первые ~4 МБ, тот же парсер. Плюс `model_info(expand=["gguf"])` для архитектуры и размера.
- Возможности: есть `mmproj-*.gguf` → `vision`; архитектура из списка аудиомоделей → `audio`; в шаблоне есть `tools` → `tools`; есть `<think>` → `reasoning`.

### 2.3. Подбор под железо (`core/advisor.py`, `assess_llm`)

```
веса       = размер выбранного GGUF
kv         = 2 · layers · kv_heads · head_dim · ctx · 2 байта
нужно_vram = веса + kv + mmproj + ~0.5 ГБ (буферы)
```

| Ситуация | План | Вердикт |
|---|---|---|
| Всё влезает в видеопамять | `gpu_layers = all` | отлично |
| Влезает ≥ 60 % слоёв | частичная выгрузка | хорошо / медленно |
| Меньше | CPU (+ немного слоёв на GPU) | медленно / очень медленно |
| Не хватает RAM | — | не хватит памяти |

Ключевая деталь: **автовыбор квантизации и контекста**. Из `quants` берём самую качественную, которая полностью влезает в видеопамять при контексте 8К; если ни одна — лучшую из тех, что дают «хорошо». Пользователь видит выбор и может переопределить («Качество: Q4 / Q5 / Q8», «Длина памяти разговора: 4К / 8К / 16К / 32К»). `Plan` дополняется полями `gpu_layers`, `ctx` (или отдельный `LlmPlan`, чтобы не задеть diffusers).

### 2.4. Список моделей «под ваше железо»

- **Встроенный каталог** `catalog.yaml`, раздел `chat` — 8–12 проверенных моделей с хорошим русским, от лёгких к тяжёлым: семейства Qwen3 (1.7B–30B-A3B), Gemma 3 (4B/12B/27B, с картинками), Qwen-VL (картинки), Llama 3.x 3B/8B, Mistral Small (картинки), русскоязычные T-lite / YandexGPT-Lite. Точные репозитории и квантизации фиксируем при реализации — удалённый каталог обновит список без новой версии программы.
- **Поиск по HF** (`hub.search("chat")`): `list_models(library="gguf", pipeline_tag in {text-generation, image-text-to-text})`, сортировка по скачиваниям; по каждому — оценка `assess_llm`, фильтр «только то, что пойдёт у меня» (уже знакомая пользователю механика вердиктов).
- **Whisper** — раздел `transcribe` в каталоге (2–3 модели).
- **Вручную**: на вкладке «Модели» — «Добавить из файла»: `.gguf` (и опционально `mmproj`), либо ID репозитория на HF → выбор квантизации из списка файлов.

На вкладке «Модели» появляются фильтры «Чат» и «Распознавание речи»; карточка чат-модели показывает выбранную квантизацию, контекст и значки возможностей (👁 картинки, 🎙 звук, 🛠 инструменты, 💭 рассуждения).

### 2.5. Ускорение ответов (решает советчик, без отдельного переключателя)

Все три приёма уже есть в закреплённой сборке `llama-server` b12320 (флаги сверены с её документацией).
`assess_llm` включает их сам и учитывает в оценке памяти и вердикте; `server_command` передаёт флаги.

| Приём | Флаги | Когда включается | Что даёт | Качество |
|---|---|---|---|---|
| **MTP** — модель угадывает несколько следующих слов, основная проверяет | `--spec-type draft-mtp` + `-md <mtp-файл>` | в репозитории модели есть файл MTP (`mtp-*.gguf`, папка `MTP/`) и он помещается в память | обычно в 1,5–2 раза быстрее ответы; измерить на RTX 3060 | не меняется: текст такой же, как без ускорения |
| **Эксперты MoE в ОЗУ** | `--n-cpu-moe N` (или `-cmoe`) | MoE-модель (`expert_count` в заголовке GGUF) не помещается в видеопамять целиком | Gemma 4 26B-A4B и Qwen3.6 35B-A3B на 8 ГБ: из «очень медленно» в «медленно» / «хорошо» | не меняется |
| **Сжатие KV-кэша до q8_0** | `-ctk q8_0 -ctv q8_0` | память под разговор мешает поместить модель в видеокарту или пользователь выбрал длинный контекст | память под разговор вдвое меньше: длиннее контекст, чаще целиком на GPU | почти не меняется |

Что нужно в коде:
- `ModelSpec`: поля `mtp` / `mtp_gb` (файл MTP в репозитории), `experts` (число экспертов из заголовка); `hub` и
  `local_import` их заполняют, `gguf.group_quants` и так не путает MTP с квантизациями. MTP скачивается вместе с моделью.
- `LlmPlan`: `draft` (путь к MTP), `cpu_moe_layers`, `kv_type`. Для MoE считать отдельно вес экспертов (в ОЗУ) и
  остальных тензоров (в видеопамяти) — оценка по слоям для них неверна.
- Проверка вживую: скорость (токены/с) с ускорением и без на RTX 3060 8 ГБ для Qwen3.5 9B, Gemma 4 12B и
  Gemma 4 26B-A4B; результат — в `Task_plan.md`.

Сознательно **не** делаем: собственное квантование (MACaQ и подобные) — нужна исходная модель в полной точности и
часы расчёта. Улучшенные готовые GGUF-файлы (например MACaQ-R) пользователь добавляет вручную, как любую модель.

### 3.2. Функции MVP

- Стриминг ответа по токенам, кнопка «Стоп» (Esc — как на других вкладках), Ctrl+Enter — отправить.
- Перегенерировать ответ, редактировать своё сообщение (ветка обрезается), копировать.
- Markdown через `QTextDocument.setMarkdown`; обновление стримящегося сообщения не чаще ~20 раз/с.
- Блок рассуждений (`<think>…</think>` / `reasoning_content`) — отдельно и свёрнут.
- **Роли (пресеты)**: «Помощник», «Промпт-инженер для картинок», «Режиссёр видео», «Сценарист», «Переводчик», «Корректор текста для озвучки» + свои. Это же основа для связей между вкладками (раздел 6).
- Параметры: температура, длина контекста, системная инструкция для чата.
- Счётчик токенов в контексте; при переполнении — старые сообщения убираются из контекста (с пометкой в интерфейсе), системная инструкция и вложения последнего сообщения сохраняются.
- История: `<data>/chats/<id>.json` (заголовок генерирует сама модель по первому сообщению, с запасным вариантом «первые слова»). Вложения копируются в `<data>/chats/<id>/files/`.

### 3.3. Вложения (`core/attachments.py`, новый)

| Тип | Что делаем | Требование к модели |
|---|---|---|
| Картинки (png/jpg/webp/bmp) | уменьшаем до ≤1536 px, отправляем как `image_url` (base64) | `vision`; иначе предлагаем сменить модель |
| Текст, код, md, csv, json | вставляем как текст с именем файла, обрезка по токенам | любая |

### 3.4. Голосовой ввод — виджет `MicButton` (`gui/widgets/mic.py`)

## 4. Безопасность и приватность

- `llama-server` слушает только `127.0.0.1`, со случайным портом и `--api-key` со случайным ключом на сессию.
- Бинарник проверяется по SHA-256 из закреплённого в программе файла; удалённый каталог не может указать другой.
- Содержимое вложений — данные для модели, не команды программе. Если модель «просит» вызвать инструмент (этап 7 и раздел 7), пользователь всегда подтверждает действие карточкой.
- Ничего из чата не уходит в сеть (кроме разовой загрузки модели/движка) — сохраняем обещание README.

## 5. Арбитр видеопамяти (обязателен до связей между вкладками)

Чат-модель (`llama-server`) и модели генерации (`GenerationWorker`) делят одну видеокарту. Без координации генерация картинки при загруженной 8B-модели упадёт по памяти.

`Services.memory` (`core/memory.py`, новый) — простая политика «одна тяжёлая модель на GPU»:

1. Перед загрузкой движка в `GenerationWorker._ensure_engine` спрашиваем арбитра. Если чат-модель занимает GPU и вместе они не влезают (`assess` + `assess_llm`) — `llama-server` останавливается (история чата не теряется; при следующем сообщении модель загрузится снова, для 4–8B это 3–10 с).
2. Перед стартом `llama-server` — то же в обратную сторону: `worker.unload_model()`.
3. Если влезают обе — держим обе.
4. Подвал боковой панели («В памяти: …») показывает обе модели и даёт выгрузить каждую.
5. Настройка «Помощник промптов на процессоре»: маленькая модель (1–3B) для улучшения промптов работает на CPU и не мешает генерации.

## 6. Взаимодействие вкладок

### 6.1. Основа: единый протокол передачи (`gui/handoff.py`)

```python
@dataclass(frozen=True)
class Asset:
    kind: str            # text | image | video | audio | file
    path: str = ""
    text: str = ""
    meta: dict = field(default_factory=dict)  # prompt, model_id, seed, duration, result_id…
    source: str = ""     # ключ страницы-источника

@dataclass(frozen=True)
class Route:
    page: str            # куда
    role: str            # prompt | reference | first_frame | attachment | voiceover | script
    label: str           # «Сделать видео из картинки»
```

- У `Page` появляются `routes(asset) -> list[Route]` и `receive(asset, role)`.
- `MainWindow.send(asset, route)` открывает страницу и вызывает `receive`.
- Меню **«Отправить в…»** у любого результата строится автоматически из `routes()` всех страниц — новые связи появляются без правки каждой страницы.
- Существующие `set_first_frame`, `apply_result` переводятся на этот протокол (поведение то же, тесты `test_gui_*` должны остаться зелёными).
- **Перетаскивание между вкладками**: результат на холсте/в галерее отдаёт `QMimeData` с файлом; поле ввода чата, `DropZone` референса и первого кадра принимают его. Перетаскивание на кнопку вкладки в боковой панели открывает её и предлагает роль.
- **Родословная**: в `Result.params` пишется `parent` (id исходного результата или сообщения чата). В «Галерее» — строка «Создано из: …» с переходом.

### 6.2. До генерации (подготовка контента)

| Где | Действие | Как работает |
|---|---|---|
| Изображение, Видео | **✨ Улучшить промпт** | Роль «Промпт-инженер» с учётом модели: теги для SD 1.5/SDXL, естественный язык для Flux/SD3, описание движения камеры для видео. Показываем «было → стало», применить/отменить |
| Изображение, Видео | **Перевести на английский** автоматически | Сейчас подсказка «модели лучше понимают английский» — убираем проблему: пишешь по-русски, переводится перед генерацией (оригинал сохраняется) |
| Изображение | Предложить негативный промпт | По модели и промпту |
| Изображение | **Промпт по картинке** (обратный промпт) | Vision-модель описывает референс → промпт для img2img/IP-Adapter |
| Озвучка | **Подготовить текст** | Корректор: ударения и «ё», раскрытие сокращений там, где `textnorm` не справился, разбивка на фразы, паузы |
| Озвучка | Перевести текст и озвучить | Перевод на язык выбранного голоса |
| Все три | 🎙 Голосовой ввод | `MicButton` из 3.4 |
| Чат | «Придумай 4 варианта…» → кнопки у каждого варианта | Ответ с пронумерованными промптами — у каждого действие «Нарисовать» |

### 6.3. После генерации (работа с полученным)

| Откуда → куда | Действие |
|---|---|
| Чат → Изображение / Видео | «Нарисовать по этому» / «Видео по этому» у сообщения или выделенного текста → промпт подставляется (с переводом и улучшением по желанию) |
| Чат → Озвучка | «🔊 Озвучить ответ» (быстро: прямо в чате плеером; полностью — на вкладку «Озвучка» с текстом) |
| Изображение → Чат | «Спросить о картинке» — вложение в новый/текущий чат |
| Изображение → Чат → Изображение | **«Оценить и улучшить»**: vision-модель сравнивает результат с промптом, предлагает исправленный промпт, кнопка «Повторить с ним» |
| Изображение → Изображение | «Использовать как референс» (img2img / стиль) |
| Изображение → Видео | уже есть (первый кадр) — переводим на протокол |
| Видео → Видео | **«Продолжить ролик»**: последний кадр (`av`) → первый кадр следующего i2v |
| Видео → Изображение | «Кадр в картинку» — текущий кадр плеера как референс |
| Видео → Чат | «Описать / придумать озвучку» — ключевые кадры в vision-модель → текст закадра |
| Озвучка → Видео | **«Наложить на видео»**: выбор ролика, склейка звука и видео через `av` (новая функция `media.mux_audio`); длина видео подстраивается под длину речи |
| Видео → Озвучка | «Озвучить ролик»: длительность ролика задаёт целевую длину текста, роль «Сценарист» пишет текст закадра |
| Галерея → любая | «Отправить в…» для любой работы, «Повторить» уже есть |

### 6.4. Сквозные сценарии (этап 8)

**«Ролик из идеи»** — мастер на вкладке «Чат» (или отдельной «Проекты»):

1. Идея (текст или голос) → «Сценарист» пишет сценарий: N сцен, у каждой промпт картинки, описание движения, текст закадра (JSON по схеме, `response_format`).
2. Пользователь правит раскадровку в таблице (сцены можно удалять/переставлять).
3. Очередь: картинки сцен → оживление (i2v) → озвучка → склейка (`av`: concat + звук) → результат в «Галерее» как одна работа с родословной.
4. Арбитр памяти последовательно выгружает LLM → diffusion → TTS; очередь уже есть в `GenerationWorker`.

Другие сценарии на том же движке: «Серия картинок в одном стиле» (общий seed/референс), «Озвученное слайд-шоу из фото» (без видеомодели — дёшево по железу).

## 7. Режим «Код»: вайб-кодинг на локальной модели

> Раздел написан для исполнителя (человека или нейросети), который будет писать код. Всё, что помечено
> **«Обязательно»**, — требования; «Можно» — на усмотрение исполнителя. Перед началом прочитать `rules.md`
> (слои `gui → workers → engines → core`, `tr()` для всех строк, `core` без Qt и torch, тесты без сети).

### 7.1. Что получает пользователь

Отдельная вкладка **«Код»** (ключ страницы `code`, иконка `code` — новый глиф `</>` в `gui/icons.py`).
Пользователь выбирает папку проекта (или создаёт новый проект из шаблона), пишет задачу словами или голосом —
«сделай страницу-визитку с тёмной темой», «добавь в бота команду /weather», «почему падает этот скрипт» —
а локальная модель читает файлы, предлагает изменения в виде наглядных правок (diff), по разрешению
пользователя применяет их и запускает команды (тесты, скрипт), видит результат и исправляет ошибки.
Всё локально, без интернета.

Три режима (переключатель `Segmented` над полем ввода):

| Режим | Что может модель | Для каких моделей |
|---|---|---|
| **Агент** | читать, искать, менять файлы, запускать команды — сама решает, что делать, шаг за шагом | только с возможностью `tools` (вызов инструментов) |
| **Правки** | возвращает блоки «найти → заменить» по файлам, которые пользователь отметил; приложение их разбирает и показывает как diff | любые, в т. ч. маленькие и без `tools` |
| **Вопрос** | только читать и искать; ничего не меняет | любые с `tools`; без `tools` — как обычный чат с прикреплёнными файлами |

Честные ожидания (показать в пустом состоянии вкладки): локальные модели 4–30B слабее облачных. Хорошо
получаются небольшие проекты: страницы HTML/CSS/JS, скрипты Python, правки в нескольких файлах, объяснение
кода и ошибок. Большие рефакторинги — плохо. При размере файла модели < 3 ГБ показывать предупреждение:
«Маленькая модель может путаться в многошаговых задачах — лучше режим „Правки“».

  `Composer`, хранение переписки), этап 5 (арбитр видеопамяти).

### 7.3. Модели и длина контекста

- **Каталог:** добавить `unsloth/Qwen3-Coder-30B-A3B-Instruct-GGUF` (MoE, специализирована на коде, умеет `tools`)
  с тегом `code`. Квантизации и параметры KV снять тем же способом, что и для остальных моделей каталога
  (заголовок GGUF через `hub.remote_header`, `gguf.group_quants`). Qwen3.5 9B и Gemma 4 12B тоже получают тег `code`.
- **Выбор модели во вкладке:** список установленных чат-моделей; сверху — с тегом `code`, затем с `tools`, затем
  остальные. Модель без `tools` → режимы «Агент» и «Вопрос» недоступны (кнопки неактивны, подсказка: «Эта модель
  не умеет пользоваться инструментами — доступен режим „Правки“»).
- **Контекст:** режим «Код» просит у советчика `assess_llm(spec, hw, ctx=32768)`; если вердикт хуже, чем при
  16384, берёт 16384, затем 8192. Выбранный контекст показывать рядом с моделью («помнит 32 тыс. токенов»).
  Если сервер уже запущен с другим контекстом — перезапустить его (через тот же менеджер сервера, что у чата).
- **Кэш подсказки:** `llama-server` переиспользует уже посчитанное начало переписки. **Обязательно:** не менять
  начало переписки между шагами агента (системная подсказка и карта проекта формируются один раз в начале
  сессии, а не перед каждым шагом). Иначе каждый шаг будет заново обрабатывать весь контекст — это секунды
  или минуты на 8 ГБ.

### 7.4. Рабочая папка (`core/code/workspace.py`) — песочница для всех операций с файлами

```python
class WorkspaceError(Exception):          # code: outside | not_found | binary | too_large | exists | ambiguous | no_match
    code: str; detail: str

@dataclass
class Change:                              # одно изменение файла; на диск ещё не записано
    path: str                              # относительный путь, всегда с "/"
    before: str | None                     # None — файла не было
    after: str | None                      # None — файл удаляется
    def diff(self) -> str: ...             # unified diff (difflib), 3 строки контекста

class Workspace:
    def __init__(self, root: Path) -> None
    def resolve(self, rel: str) -> Path                       # см. правила ниже
    def tree(self, max_entries: int = 400) -> list[str]       # отсортированные относительные пути
    def read(self, rel: str, start: int = 1, end: int | None = None) -> str   # с номерами строк
    def search(self, pattern: str, glob: str = "", max_hits: int = 100) -> list[tuple[str, int, str]]
    def propose_write(self, rel: str, content: str) -> Change              # новый файл или полная замена
    def propose_edit(self, rel: str, old: str, new: str, replace_all: bool = False) -> Change
    def propose_delete(self, rel: str) -> Change
    def apply(self, change: Change) -> None                   # единственный метод, который пишет на диск
```

Правила (**обязательно**, каждое покрыть тестом):
- `resolve`: путь относительный; `(root / rel).resolve()` должен лежать внутри `root.resolve()`
  (`is_relative_to`), иначе `WorkspaceError("outside")`. Абсолютные пути, `..`, символические ссылки и
  junction-точки наружу — отказ. Имена устройств Windows (`CON`, `NUL`, `COM1`…) — отказ. Любая запись в `.git/` — отказ.
- `tree`: пропускать `.git`, `node_modules`, `.venv`, `venv`, `__pycache__`, `dist`, `build`, `.idea`,
  `.mypy_cache`, `.pytest_cache`, плюс простые шаблоны из корневого `.gitignore` (`fnmatch`, без полной
  семантики git). Больше `max_entries` — обрезать и добавить строку `… и ещё N файлов`.
- `read`: не больше 400 строк за вызов и 1 МБ файла; формат строк `  12| текст`. Если файл длиннее — в конце
  `[показаны строки 1–400 из 1250; запросите следующие через start/end]`. Двоичный файл (нулевой байт в первых
  8 КБ) — `WorkspaceError("binary")`.
- Кодировка: читать как UTF-8 (с BOM или без), при ошибке — `cp1251` (у русских пользователей много таких файлов).
  **Запись сохраняет исходные кодировку, BOM и окончания строк (CRLF/LF)** — модель всегда работает с `\n`,
  преобразование при `apply`.
- `propose_edit`: `old` должен встречаться в файле ровно один раз (если `replace_all=False`). Ноль совпадений —
  ещё одна попытка с нормализацией пробелов в концах строк; не помогло — `WorkspaceError("no_match")` с
  подсказкой модели «прочитайте файл заново». Больше одного — `WorkspaceError("ambiguous")` с номерами строк.
- `search`: регулярное выражение Python, только текстовые файлы из `tree`, максимум `max_hits` совпадений,
  строка совпадения обрезается до 200 символов.

### 7.5. Инструменты для модели (`core/llm/tools.py` + `core/code/tools.py`)

Общий механизм (`core/llm/tools.py`):

```python
@dataclass(frozen=True)
class Tool:
    name: str
    description: str                      # по-английски: модели понимают инструменты лучше на английском
    parameters: dict[str, Any]            # JSON Schema
    handler: Callable[[dict[str, Any]], ToolOutcome]
    approval: str = "none"                # none | write | command

@dataclass
class ToolOutcome:
    text: str                             # то, что увидит модель (обрезается до 6000 символов: начало + конец)
    change: Change | None = None          # для approval == "write": что показать пользователю
    command: str = ""                     # для approval == "command"

def openai_schema(tools: list[Tool]) -> list[dict[str, Any]]   # формат {"type": "function", "function": {...}}
```

Набор инструментов режима «Код» (`core/code/tools.py`, функция `code_tools(workspace, runner, mode) -> list[Tool]`):

| Инструмент | Параметры | Подтверждение | Режимы |
|---|---|---|---|
| `list_files` | `path` (необязательно) | нет | все |
| `read_file` | `path`, `start`, `end` | нет | все |
| `search` | `pattern`, `glob` | нет | все |
| `write_file` | `path`, `content` | правка | Агент |
| `edit_file` | `path`, `old_text`, `new_text`, `replace_all` | правка | Агент |
| `delete_file` | `path` | правка (всегда, даже при автоприменении) | Агент |
| `run_command` | `command`, `timeout_s` (≤ 600) | команда (всегда) | Агент |
| `finish` | `summary` | нет | Агент — модель сообщает, что задача сделана |

Ошибка инструмента — **не исключение для цикла**: возвращается моделью как текст `ERROR: <code>: <пояснение>`,
чтобы она могла исправиться. Сетевых инструментов нет (загрузки, браузер) — сознательно.

### 7.6. Цикл агента (`core/code/agent.py`) и поток (`workers/code_agent.py`)

**Изменение клиента** (`core/llm/client.py`): `Delta` получает поле `tool_calls: list[dict]` — фрагменты
`choices[0].delta.tool_calls` как есть. Склейка по `index`: `id` и `function.name` из первого фрагмента,
`function.arguments` — конкатенация строк. Запрос: `tools=[...]`, `tool_choice="auto"`,
`parallel_tool_calls=False` (локальные модели надёжнее по одному вызову), `temperature=0.2`.

Алгоритм `AgentLoop.run(task: str)`:

```
messages = история сессии + {"role": "user", "content": task}
for step in 1..MAX_STEPS (30):
    ответ = client.chat(messages, tools=schema, ...)       # текст стримится в UI сигналом
    messages += assistant-сообщение (content + tool_calls)
    если tool_calls нет  → конец (stop_reason = "done")
    для каждого вызова:
        args = json.loads(arguments); не разобралось → результат "ERROR: invalid_arguments: ..." 
        outcome = tool.handler(args)
        если tool.approval != "none" → ждать решения пользователя (см. ниже)
        messages += {"role": "tool", "tool_call_id": id, "content": outcome.text}
        если вызван finish → конец (stop_reason = "done")
    если тот же вызов с теми же аргументами повторился 3 раза подряд → добавить сообщение-подсказку
        "You are repeating the same action; try a different approach or call finish";
        5 раз → конец (stop_reason = "loop")
    если prompt_tokens из usage > 75 % контекста → сжатие (7.8)
конец по MAX_STEPS → stop_reason = "step_limit" (пользователю: «Модель сделала 30 шагов. Продолжить?»)
```

**Подтверждения.** `AgentWorker(QThread)` выполняет цикл. Когда нужно решение — сигнал
`approval_needed(request_id: int, kind: str, payload: dict)` (`kind`: `write` с `diff`, `command` с текстом
команды) и ожидание `threading.Event`. Интерфейс вызывает `worker.resolve(request_id, decision, note="")`,
`decision`: `apply` | `reject` | `apply_all_session` (только для правок) | `allow_session` (только для команд —
запоминается точная строка команды). Результат для модели: `applied` / `rejected by the user: <note>` / вывод
команды. «Стоп» (Esc) снимает ожидание и завершает цикл с `stop_reason = "cancelled"`; запущенная команда
убивается вместе с дочерними процессами.

Сигналы `AgentWorker`: `text(str)`, `reasoning(str)`, `tool_started(call_id, name, args)`,
`tool_finished(call_id, text)`, `approval_needed(...)`, `change_applied(path)`, `finished(stop_reason, usage)`,
`failed(code, detail)`.

### 7.7. Режим «Правки» — для моделей без инструментов (`core/code/edit_blocks.py`)

Системная подсказка просит модель отвечать блоками ровно в таком формате:

```
path/to/file.py
<<<<<<< SEARCH
старый фрагмент (точно как в файле)
=======
новый фрагмент
>>>>>>> REPLACE
```

Пустой `SEARCH` — создать файл с содержимым `REPLACE` (если файл есть — ошибка). Разбор:
`parse_blocks(text) -> list[EditBlock(path, search, replace)]`, устойчивый к ```-ограждениям вокруг блока и
к пробелам после маркеров. Каждый блок превращается в `Change` через `Workspace.propose_edit` /
`propose_write` и показывается как diff с кнопками. Блок, который не применился (`no_match`), показывается
красным с кнопкой «Попросить модель исправить» — она отправляет модели текст ошибки и актуальное содержимое
файла. В контекст режима «Правки» входят файлы, которые пользователь отметил галочками в дереве (их
содержимое целиком, с ограничением по токенам — превышение показывается до отправки).

### 7.8. Контекст: карта проекта и сжатие

- **Карта проекта** (`core/code/repomap.py`, `repo_map(workspace, budget_chars=6000) -> str`): дерево файлов и
  краткое оглавление кода — для Python через `ast` (классы, функции с аргументами), для JS/TS — регулярными
  выражениями (`function x(`, `class X`, `export const x =`), для остальных — только имя файла. Обрезка по
  бюджету: сначала убираются оглавления дальних от корня файлов, потом сворачиваются папки. Кэш по `mtime`.
  Карта вставляется **один раз** в начале сессии (см. 7.3 про кэш); после применённых правок модель узнаёт о
  них из результатов инструментов. Файлы `.env*`, ключи и `*.pem` в оглавление не попадают.
- **Сжатие переписки** (когда занято > 75 % контекста): модели отправляется отдельный запрос «кратко изложи,
  что уже сделано, какие файлы изменены и что осталось» (без инструментов, ≤ 800 токенов); старые сообщения
  заменяются этой сводкой, последние 6 сообщений остаются как есть. Пользователь видит в ленте отметку
  «Начало разговора сжато». Сжатие ломает кэш подсказки — поэтому только по порогу.
- **Оценка токенов до отправки:** `len(text) / 3.5`; точное число — из `usage` ответа.

### 7.9. Команды (`core/code/commands.py`)

```python
@dataclass
class CommandResult:
    exit_code: int | None; output: str; timed_out: bool; truncated: bool

def run_command(command: str, cwd: Path, timeout_s: float = 120,
                cancelled: Callable[[], bool] = lambda: False) -> CommandResult
```

- Запуск через оболочку (`shell=True`: на Windows — `cmd.exe`), рабочая папка — корень проекта,
  `CREATE_NO_WINDOW`, stdout и stderr вместе, `PYTHONIOENCODING=utf-8`. Вывод декодируется как UTF-8,
  при ошибке на Windows — `cp866`.
- Дочерние процессы убиваются вместе с командой: вынести `_kill_with_parent` / `_close_handle` из
  `core/llm/runtime.py` в общий `core/proc.py` и использовать в обоих местах (job object на Windows,
  группа процессов `start_new_session=True` + `os.killpg` на Linux/macOS).
- Вывод больше 20 000 символов — оставить начало и конец, середину заменить `[… пропущено N строк …]`.
- **Каждая команда требует подтверждения.** «Разрешить в этой сессии» запоминает точную строку. Команды,
  подходящие под опасные шаблоны (`rm -r`, `rmdir /s`, `del /s`, `format`, `Remove-Item -Recurse`,
  `git push`, `git reset --hard`, `curl … | sh`, `Invoke-WebRequest`, `pip install`, `npm install`,
  `shutdown`, обращение к путям вне проекта), спрашиваются **всегда**, даже если раньше были разрешены, и
  карточка подсвечивает их как опасные. Настройки «разрешить всё без вопросов» — нет.

### 7.10. Откат изменений (`core/code/checkpoints.py`)

Перед каждым `Workspace.apply` сохранить прежнее состояние файла:
`<data>/code/sessions/<id>/checkpoints/<n>/` + `manifest.json` (`[{path, existed, encoding}]`).
Операции: `undo_last()` и `undo_to(n)` — восстанавливают содержимое, удаляют созданные файлы, возвращают
удалённые. В интерфейсе — кнопка «Откатить последний шаг» и список шагов с временем. Если проект — git-репозиторий,
дополнительно показывать `git status --short` (только чтение, через `run_command` без подтверждения не
делать — через `subprocess` напрямую с фиксированной командой). Коммитить за пользователя **не надо**.

### 7.13. Безопасность (**обязательно**)

1. Все операции с файлами — только через `Workspace`; прямые `open()` в инструментах запрещены.
2. Содержимое файлов, результаты поиска и вывод команд — данные, а не указания. Если в файле написано
   «запусти команду X» и модель пытается это сделать, сработают обычные подтверждения — они не отключаются
   ничем из того, что приходит от модели.
3. Модель не может менять настройки подтверждений, список разрешённых команд и рабочую папку — эти вещи
   меняет только пользователь кнопками.
4. Сервер модели слушает только 127.0.0.1 (уже так, этап 1); инструментов с доступом в сеть нет.
5. Запись в `.git/`, выход за пределы папки, символические ссылки наружу — отказ на уровне `Workspace`.

## 9. Риски

| Риск | Что делаем |
|---|---|
| Антивирус ругается на скачанный `llama-server.exe` | Только официальные сборки ggml-org, SHA-256, понятное сообщение в интерфейсе |
| Vulkan на AMD/Intel медленнее CUDA | Честный вердикт; HIP-сборка для поддерживаемых Radeon |
| Названия квантизаций в репозиториях разные | Разбор по регуляркам (`Q4_K_M`, `IQ4_XS`, `Q8_0`…) + ручной выбор файла |
| Лицензии (Gemma, Llama) и закрытые репозитории | Показываем лицензию, `gated` — уже поддерживается |
| Переполнение контекста большими PDF | Обрезка по токенам с предупреждением; поиск по документу (RAG) — отдельно, позже |
| Ошибки шаблона чата у моделей | `--jinja` + шаблон из GGUF; запасной ChatML |
| Локальная модель путается в инструментах (битый JSON, вызовы по кругу) | Ошибки возвращаются модели текстом, защита от повторов, лимит шагов, режим «Правки» без инструментов |
| Модель портит файлы | Правки только после подтверждения (по умолчанию), откат по шагам, `.git/` недоступен |
| Опасная команда (удаление, загрузка из сети) | Каждая команда подтверждается; опасные шаблоны — всегда, с подсветкой; нет режима «без вопросов» |

| Медленная обработка длинного контекста на 8 ГБ | Неизменное начало переписки (кэш), карта проекта вместо целых файлов, сжатие KV (этап 1.5) |
